# SPK Memory Arbitration v0

Status: DRAFT
Baseline: spk-core-network-v0
Parent: spk-memory-access-model-v0.md

## 1. Purpose

Define deterministic architectural memory
service arbitration for SPK Processing Elements.

This contract is independent of simulator
implementation language and host memory.

## 2. Service units

MemoryServiceRequestV0.service_units represents
abstract service demand.

ProcessingElementV0.accesses_per_service_tick
represents the number of these abstract service
units available per SERVICE_TIME cycle.

Both quantities must use the same architectural
unit under the selected cost profile.

These units are not bytes or CPU instructions.

## 3. Initial workload model

A4 v0 processes a finite request set.

All requests are ready at SERVICE_TIME tick zero.

Dynamic arrivals are outside A4 v0.

Each target PE has an independent service budget.

Interconnect contention is not yet modeled.

## 4. Priority policy

Priority is derived from authorized activity.

Default classes:

P0 EXECUTE, ROUTER
P2 LEARN
P3 VERIFY
P4 REMODEL
P5 OBSERVER

P1 is reserved for future activation control.

Smaller priority numbers receive service first.

Within a class, requests are ordered by
principal_id and request_id.

Request order in the input tuple must not
affect the arbitration result.

## 5. Service accounting

A request may require multiple service ticks.

Service may be split into integer service units.

A request becomes complete only after all
required service units have been assigned.

Partial service does not imply a partial
architectural memory mutation.

Every service slice must satisfy PE capacity.

No service units may be created or discarded.

## 6. Temporal separation

SERVICE_TIME measures resource service cycles.

EVENT_TIME remains unchanged.

A4 does not schedule neuronal execution.

Therefore A4 alone does not prove preservation
of the complete Network v0 causal execution order.

Functional integration requires separate tests.

## 7. Resource exhaustion

A maximum service-tick budget may be imposed.

An insufficient budget rejects the workload
before service begins.

No partial result is reported as successful.

This is a simulation execution budget,
not a memory buffer-capacity model.

## 8. Determinism and limitations

Identical requests, architecture and priority
policy must produce identical service records.

Fixed priority is deterministic but does not
guarantee starvation freedom under unbounded
future arrivals.

Access authorization occurs before arbitration.

A4 assumes service requests were generated by
the authorized transaction mapping layer.

A4 is not an independent authentication boundary.

## 9. Acceptance

Required tests:

A4-01 Priority precedence
A4-02 Capacity per PE and service tick
A4-03 Multi-tick service
A4-04 Input-order independence
A4-05 Independent PE service
A4-06 EVENT_TIME preservation
A4-07 Duplicate request rejection
A4-08 Unknown PE rejection
A4-09 Invalid service demand
A4-10 Execution budget rejection
A4-11 Service accounting conservation
A4-12 Empty workload

# SPK S3.7d/3b2b2k/12 · Dynamic Destination Inventory v0

Status: **candidate** until the complete test gate on fwork passes. No changes to frozen Core/Network/Compiler.

## Why this boundary exists

An event resident in EVENT has been admitted by the physical storage controller. A route generated by Core may also be STAGED, pending in OUTPUT, or already consumed. These are different architectural facts. Merely grouping currently resident events by `(node, EVENT_TIME)` **cannot prove a batch is complete**: another emitter could later generate an event with the same EVENT_TIME while stalled by backpressure in SERVICE_TIME.

## Contract

`derive_dynamic_destination_inventory_v0(architecture, registry, storage)` creates a **read-only**, deterministic, immutable inventory of all Core-derived route identities owned by `OwnedDynamicServiceRegistrationStateV0`. For each destination `(epoch, node, PE, delivery EVENT_TIME)` it records:

- one identity per physical route, retaining parallel-edge multiplicity;
- stage `STAGED` (request registered, no physical occurrence), `OUTPUT` (published and resident at source), `EVENT` (admitted at target), or `CONSUMED` (physical tombstone);
- the exact target channels currently resident in EVENT, with duplicates;
- `closure_status='OPEN_UNPROVEN'` without exception and `supports_consume_admission=False`.

It validates the architecture profile and finite storage capacity, compares physical routed occurrence payloads byte-for-byte against Core-derived allocated occurrences, rejects unregistered dynamic identities (including mistakenly using an `EMISSION_RECORD` ID as route ID), and does not conflate static IDs with the new dynamic namespace. Unrelated static storage identities below the dynamic namespace are reported separately.

**Trust boundary**: the supplied `RoutedStorageStateV0` must be taken from the actual authoritative backpressure controller. The function cannot cryptographically authenticate a hand-built state; it is a typed reconciliation tool, not storage authority.

## Non-goals, critical

- No `BATCH_CONSUME` is created, authorized, started, or confirmed.
- No route gets bound to a `target_batch_index`; no `RoutedBindingManifestV0` is created.
- No declaration of batch completeness, including when all **currently registered** routes have arrived. Future routes can be generated by Core.
- External ingress is not yet included; it needs the actual admission ledger and a merge/closure policy.
- No CLOCK/BARRIER policy is silently assumed. `EVENT_TIME` is not `SERVICE_TIME`.
- No physical capacity is reserved and no effect is performed by this inventory.

## Next acceptance criterion

Build a **sound batch-closure policy** that accounts for future same-EVENT_TIME emissions and external ingress. Only after obtaining a closure proof from the single-owner scheduler should dynamic `BATCH_CONSUME` requests be created and linked to the registered routes; then admit them to the real storage controller. Finite observation or tick-limit is not a closure certificate.
